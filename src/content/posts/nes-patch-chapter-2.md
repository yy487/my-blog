[上一章](https://blog.yychess.top/posts/2026-10-12-/)讲到了 PRG、CHR、PPU 和 Mapper，也算了一下中文字库的大小：一个 16×16 汉字需要四个 Tile，展开成 NES 的图案数据就是 64 字节。字一多，PPU 那个 8 KiB 的图案窗口根本放不下。

这一章就把这些东西放到实际的补丁里，看看一个汉字怎样从 PC 上的字体，走到游戏的对话框中。

这次处理的游戏是《水晶之龙》。我的做法是把译文和字模放进 PRG，提前按屏幕大小分页，运行时只上传当前页需要的字形。场景和文字各用一组 CHR 图案，通过 MMC5 在画面中途切换。

整条流程可以先记成下面这样，后面逐段展开：

```text
UTF-8 译文
    ↓ PC 端排版、收集本页字符、生成字模
页面包与页目录 → 放入 PRG
    ↓ 6502 读取当前页
页头复制到 RAM，字模按需读取
    ↓ NMI 中分批上传
CHR-RAM 中的当前页字库
    ↓ 扫描线中断切换映射
屏幕下方显示中文
```

## 1. 先把 FDS 的文件装载接起来

《水晶之龙》原版是 FDS 游戏。它把程序、场景、图案等资源放在磁碟文件里，运行时再装载到 CPU RAM 或 CHR-RAM。

我先把它转换成 NES 2.0 / Mapper 5，也就是 MMC5 镜像。原磁碟文件变成 PRG 中的资源块，由新的装载驱动把内容复制回原来的装载地址。原脚本继续在原来的 RAM 地址执行。

固定 Bank 中保存了资源描述符，装载器根据盘面号和文件 ID 找到资源。每条描述符记录起始 Bank、原文件类型、装载地址、长度等信息。这样原游戏发起一次资源读取时，新驱动就能从 PRG 中找到对应的内容。

这里把 PRG 窗口设为 8 KiB，CPU 看到的主要布局如下：


| CPU 地址 | 当前用途 |
| ------------- | --------------------------------- |
| `$6000–$7FFF` | PRG-RAM Bank 0，原程序的 RAM 执行区域 |
| `$8000–$9FFF` | PRG-RAM Bank 1，原资源和中文单页渲染器 |
| `$A000–$BFFF` | 通常是 PRG-RAM Bank 2，装载资源时临时映射 ROM |
| `$C000–$DFFF` | 在原游戏 RAM Bank 3 与中文 PRG Bank 之间切换 |
| `$E000–$FFFF` | 固定 ROM Bank，保存装载器、中断和中文分派程序 |


后面最常用的就是 `$C000–$DFFF` 这个窗口。向 MMC5 的 `$5116` 写入 `$03`，这里看到的是原游戏 RAM；写入 `$80 | bank`，这里看到的就是指定 PRG Bank。

负责切换的程序放在固定 Bank 中。窗口换了，它自己的代码仍然在 `$E000–$FFFF`，可以接着执行。

## 2. 一个汉字为什么既是 32 字节，又是 64 字节

先看这次实际生成的“龙”字：

![16×16 的龙字字模，中间的两条线把它分成四个 8×8 象限](/uploads/nes-chapter-2/glyph-dragon.png)

PC 端使用 Windows GDI，把字符绘制到一张 16×16 的位图里。默认字体为 SimHei，关闭抗锯齿，白字黑底。读出像素后，笔画记为 1，空白记为 0。

一个字符有 256 个像素，保存这张单色位图需要：

**16 × 16 ÷ 8 = 32 字节。**

每行两个字节，先存左边的 8 个像素，再存右边的 8 个像素；每个字节的最高位对应最左侧像素。空格的 32 个字节全部为 0。

到了 NES 这边，图案仍然要按两个位平面保存。一个 16×16 字被拆成左上、右上、左下、右下四个 Tile，每个 Tile 需要 16 字节，所以最后写入 CHR-RAM 的大小是：

**4 × 16 = 64 字节。**

展开时，四个象限在原字模中的起始偏移依次是 `0、1、16、17`，每隔两个字节读取下一行。这个过程可以用几行 Python 表示：

```python
offsets = (0, 1, 16, 17)  # 左上、右上、左下、右下

for offset in offsets:
    plane = bytes(glyph[offset + 2 * row] for row in range(8))
    tile = plane + plane
```

这里把同一份 8 行数据分别写进两个位平面。某个像素为 1 时，两平面组成 `11`，颜色编号就是 3；空白组成 `00`，颜色编号就是 0，再由调色板决定实际颜色。

所以这套实现里，**PRG 每个字存 32 B，CHR-RAM 每个字占 64 B**。两个位平面的展开工作留到上传时完成。

字库还保留了一份 `Unicode → 字模` 的对应关系。再次导入译文时，已有字模直接复用，只为缺少的字符生成新字形，手工调整过的笔画也就能留下来。

## 3. 把整套字库的问题，缩小成当前这一页

这个游戏的中文显示区安排为 **13 列 × 3 行**。使用 16×16 字体后，实际文字矩形就是 208×48 像素，一页最多显示 39 个字符格。

PC 端先完成分页，再给每一页单独建立一个 `alphabet`，保存这一页会用到的字模。第 0 项固定为空格，其他字符按首次出现的顺序加入；同一页重复出现的字共用一个编号。

例如一页里出现多次“龙”，显示数据只需要多写几次它的编号，字模仍然只有一份。

39 个显示格，最多引入 39 个不同的非空格字符，加上空格，一页的字模数上限就是 **40**。于是运行时需要准备的缓存大小也确定了：

**40 × 64 = 2560 字节，也就是 160 个 Tile。**

6502 读取的是页内的一个字节编号，然后据此找到四个 Tile。Unicode 查询、字体生成和分页，都已经在 PC 端做完。

### 正文和画面里的空格要分开保存

排版时还要处理换行。我给页面保留了两份序列：


| 数据 | 保存什么 |
| --------- | ------------------ |
| `logical` | 输入的正文和换行 |
| `cells` | 最终显示的字符格，包括排版补上的空格 |


例如输入：

```text
龙来了
快逃
```

第一行用了 3 格。遇到换行后，`cells` 补上 10 个空格，让“快逃”从下一行开始；`logical` 则保留原来的一个换行。逻辑序列中用 `$FE` 表示 LF。

这样从成品 ROM 重新导出时，就能还原原来的正文和换行。排版补出的空格留在显示层，不会混进译文。

## 4. 原文本入口只留下一个 10 字节引用

解决了字模，接下来就是译文的长度。

如果还把中文塞回原日文所在的字节槽，译文一长就会挤到下一段数据。我把正文移到新的 PRG 空间，让原文本表指向一个短引用，再通过这个引用找到分页后的内容。

当前使用的 V3 引用一共 10 字节：


| 字段 | 长度 |
| ------------------------------------ | --- |
| 格式标记 `02 5A 48 03`，其中 `5A 48` 是 `ZH` | 4 B |
| 页目录所在 Bank | 1 B |
| 页目录地址 | 2 B |
| 页面总数 | 2 B |
| 结束标记 `$FF` | 1 B |


原文本表继续使用原来的 16 位小端指针。回注时更新表项，让它指向这个引用；原位置放不下 10 字节时，就在 DATA 末尾追加引用，再更新指针。

页目录的每一项只有 3 字节：一个 Bank 编号，加一个 16 位页面地址。页面包里保存本页的显示索引、字模地址、逻辑正文、Unicode 映射和字模数据。

这些内容的分工也很明确：显示索引和字模供游戏渲染，逻辑正文和 Unicode 映射供工具重提取。

设显示格数为 `C`、逻辑 Token 数为 `L`、本页字模数为 `N`，页面包总长为：

```text
页面字节数 = 17 + C + L + 4N + 32N
           = 17 + C + L + 36N
```

一页 39 个不同正文字符，加上空格，共 40 个字模；这时 `C = 39`、`L = 39`，页面包是：

**17 + 39 + 39 + 36 × 40 = 1535 B。**

文本变长后，增加的是页数和 PRG 中的页面数据。比如测试中的一条 1031 字、无换行文本，需要 27 页，目录占 `27 × 3 = 81 B`，DATA 中仍然只有那个 10 B 引用。

## 5. 把页面放进 PRG，再把页头搬到 RAM

页面包按照 8 KiB Bank 分配，**一个页面包完整放在一个 Bank 内**。当前 Bank 的尾部余量不足时，用 `$FF` 补到边界，再从下一个 Bank 开始放。

这样在上传同一页的字模时，源地址一直落在 `$C000–$DFFF` 窗口里。

页目录则允许跨 Bank。比如从 `$DFFE` 开始读取，取出两个字节后，下一个字节就要到下一个 Bank 的 `$C000` 继续读。目录读取函数每取一个字节都会推进地址，到 `$E000` 时递增 Bank 并回到 `$C000`。

假定页面位于 PRG 的第 `b` 个 8 KiB Bank，映射后的 CPU 地址为 `a`，在这份带 16 B 文件头的镜像中，对应文件偏移是：

```text
文件偏移 = 16 + 8192 × b + (a - $C000)
```

PRG 增长时还要移动固定 Bank：


| PRG 大小 | 8 KiB Bank 数量 | 最后一个 Bank | `$5117` 初始化值 |
| ------- | ------------- | --------- | ------------ |
| 512 KiB | 64 | 63 | `$BF` |
| 1 MiB | 128 | 127 | `$FF` |


重建程序会更新资源描述符，并把固定 Bank 搬到新的末尾。当前这批成品的 PRG 仍是 **512 KiB**；本轮数据超过这个容量时，工具才会扩到 1 MiB。

页面独立保存字模，也会带来重复占用：同一个汉字出现在不同页面时，每个页面包都会带上一份字模。因此实际 PRG 占用要按各页字模数相加，不能只统计整份译文出现了多少个不同汉字。

增量修改还会留下旧页面包。批量定稿时从基础镜像重新构建，可以避免把这些旧数据一轮轮积累进成品。

### 页头为什么还要复制一遍

中文入口从原文本指针识别出 V3 引用后，就可以根据目录找到页面。但是 `$C000–$DFFF` 还承担着原游戏的 RAM 映射，中断处理时会切回 RAM。

如果旧渲染器一直把这个窗口当作页头读取，映射变化后，同一个地址就会读出另一份数据。

因此分派器先把页头和显示索引复制到 `$A120`。需要复制的长度为 `15 + C`，最多 54 B，之后旧渲染器从这段 RAM 缓冲工作。

```text
从目录取出本页的 Bank 和地址
    ↓
把本页 Bank 映射到 $C000–$DFFF
    ↓
复制 15 + C 字节到 $A120
    ↓
把 $C000–$DFFF 恢复成 RAM Bank 3
    ↓
让单页渲染器从 $A120 读取页头和显示索引
```

页头中的字模指针仍然指向 PRG。上传字模时，再把对应 Bank 映射回来取数据。逻辑正文和 Unicode 表留在 ROM 中，运行时不必复制它们。

## 6. NMI 打断之后，Bank 得原样还回来

前台程序可能正在读页目录，NMI 就来了；NMI 自己也要运行原游戏的 RAM 逻辑，还要上传中文字模。同一个窗口在几种用途之间来回切换，必须记住每次切换前的状态。

这份驱动用 `$9FD1` 保存 `$5116` 的影子值，所有中文窗口切换都经过同一个函数：

```text
set_bank:       ; A 中放入要写入的 Bank 选择值
    STA $9FD1   ; 先保存软件影子值
    STA $5116   ; 再修改 MMC5 映射
    RTS
```

一次 NMI 中，映射按下面的顺序变化：


| 时点 | `$C000–$DFFF` 的内容 |
| ----------- | ------------------------- |
| 前台读取页面 | 当前中文 PRG Bank |
| NMI 入口 | 保存被打断时的映射，然后切到 RAM Bank 3 |
| 字模上传前 | 临时切到本页字模所在的 PRG Bank |
| 一个 Tile 上传后 | 切回 RAM Bank 3，继续原游戏任务 |
| NMI 出口 | 恢复进入中断时保存的映射 |


NMI 返回后，前台程序还要从被打断的位置接着取数，因此必须恢复原来的 Bank 映射。

目录读取还有一组同样需要保存的东西：零页指针。目录函数使用 `$14/$15`，把 `$00/$01` 留给页面指针。否则取出一条目录记录的过程中，就可能把刚组装好的页地址覆盖掉。

## 7. 把字模上传到 CHR-RAM，再切换文字区

页内第 `g` 个字模使用四个连续 Tile，起始编号为：

```text
起始 Tile ID = $25 + 4 × g
```

四个编号依次对应左上、右上、左下、右下。构建文字缓冲时，把显示索引乘 4，再加上 `$25`，得到左上 Tile 的编号；另外三个编号依次加 1、2、3，写入 Nametable 中相邻的两行、两列。

对应的 CHR 上传地址为：

```text
目标地址 = $1250 + 64 × g + 16 × q
```

其中 `q` 是 0 到 3，表示当前上传哪个象限。`$1250` 对应从第二张图案表中的 `$25` 号 Tile 开始存放字形。

当前驱动每次 NMI 上传一个 16 B Tile：通过 `$2006` 设置目标地址，再经 `$2007` 写入两个位平面。四个象限上传完，原单色字模指针增加 32，继续下一个字。

一页 `N` 个字模需要 `4N` 次上传。全部字模准备好后，再提交对应的文字缓冲。

### 场景与文字各用一组图案

如果把中文写进场景正在使用的图案区，场景中引用这些 Tile 的位置也会变。这里使用两组 CHR 映射：


| CHR 组 | 物理页 | 用途 |
| ----- | ------------ | ------- |
| 场景组 | 1 KiB 页 0–7 | 原场景图案 |
| 中文组 | 1 KiB 页 8–15 | 当前页中文字模 |


两组各构成一个 8 KiB 视图，放在目标镜像的 32 KiB CHR-RAM 中。每帧开始先使用场景组，再通过 MMC5 扫描线 IRQ，在第 160 行切到中文组。

寄存器设置为 `$5203 = 160`、`$5204 = $80`。实际文字区域位于屏幕 `x = 24–231`、`y = 160–207`，对应前面的 208×48 像素。

上传期间 `READY = 0`，隐藏还没有准备好的文字区。清屏、字模上传和文字缓冲提交全部完成后，才设置 `READY = 1`，显示整页文字。

## 8. 翻页、道具和退出后的状态交接

文字显示出来后，还要让游戏流程继续往下走。

普通剧情文本每显示完一页，就等待一次新的 A 键按下，最后一页也一样。这里检测的是按下沿：

```text
新按下的 A = (当前按键 XOR 上次按键) AND 当前按键 AND $80
```

这份驱动的 A 键位是 `$80`。一直按住 A 时，这个表达式不会持续成立，因而不会连续跳过好几页。

道具说明的末页则直接返回原菜单，返回前还要刷新按键状态，让翻页用过的 A 不再被菜单当作一次新的确认。自动加载提示的末页也直接返回。

### 道具图标需要每行避让

道具页左侧还有图标，所以每一行先留三个空格，正文容量变成：

**(13 − 3) × 3 = 30 格。**

![金钱说明的每一行都从图标右侧开始，原游戏状态仍显示持有 100 克雷迪特](/uploads/nes-chapter-2/money-final.png)

这个缩进由排版标记控制，保存在页面数据里。`logical` 中的正文仍然是“钱。持有１００克雷迪特。”，显示层再为每行补上缩进。

道具名称和状态还牵涉原脚本的地址关系。我保留原字符串，用一张“原 CPU 地址 → 中文 V3 引用”的表，替换最后显示出来的文字。道具选择和金钱数额继续由原变量决定。

### 退出时把原引擎的状态交回去

中文路径修改过文字缓冲、字模索引、NMI 绘制任务和分屏状态。退出时要清理这些内容，重建原文字状态，并把进入分派器时保存的文本指针恢复回去。

序章的入口会连续运行标题和叙事，因此恢复工作要放在这段过程返回之后。提前清理的话，后面的文字显示仍会重新写入中文状态，首个场景就会继承这份状态。

恢复时，先保留要交还上层的文本指针，关闭中文模式和分屏，清空字模计数与绘制状态，再重新初始化原来的文字系统、排入清屏任务。等绘制完成后，恢复文本指针，交回原引擎。

这一步可以直接从操作上检查：结束序章后，人物是否能移动；退出道具说明后，菜单是否能继续响应。文字能画出来与事件能继续执行，分别依赖显示过程和退出时的状态交接。

## 9. 从画面现象定位问题

下面是序章连续两页的实际效果。场景保持原样，变化集中在下方的文字区：


| 第 1 页 | 第 2 页 |
| -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| ![序章第 1 页，显示水晶之龙袭来及穿梭机失控的文字](/uploads/nes-chapter-2/intro-page-1.png) | ![序章第 2 页，承接强烈冲击和眼前一片漆黑，提示按 A 键](/uploads/nes-chapter-2/intro-page-2.png) |


调试时，可以先用页面中的显示索引和字模，在 PC 上拼出一张 208×48 的文字图，再对照模拟器中的图案表和最终画面。这样就能沿着数据经过的顺序，把问题逐段缩小：


| 观察到的现象 | 先检查什么 |
| ---------------------- | ------------------------------------ |
| PC 上拼出的字形就缺笔、左右颠倒或四块错位 | 单色字模的位序，以及四个象限的拆分和排列 |
| PC 上的图正确，模拟器图案表里的字形错误 | 字模源 Bank、上传地址和位平面写入顺序 |
| 图案表中的字形正确，画面上排列或颜色错误 | Nametable 中的 Tile 编号、调色板和显示时的 CHR 映射 |
| 中文正确，场景却出现花块 | 中文与场景是否写到了同一组图案，分屏和每帧映射恢复是否正确 |
| 按住 A 连跳几页，或显示结束后操作失效 | 按下沿检测、原文本指针和文字任务的退出状态 |


排查顺序也由此确定：先核对字模，再核对上传后的 Tile，最后看画面组合和事件返回。

## 10. 从这一屏文字算起

拿上面的序章第一屏来说，三行文字占满了 39 格。其中“失”“了”“！”有重复，复用这些字形后，再加上预留空格，一共需要 36 个字模。

这一屏的字形开销就可以直接算出来：


| 位置或操作 | 开销 |
| ----------------- | --------------------- |
| PRG 中保存单色字模 | `36 × 32 = 1152 B` |
| CHR-RAM 中保存展开后的字形 | `36 × 64 = 2304 B` |
| 把全部字形上传到 CHR-RAM | `36 × 4 = 144` 个 Tile |


当前驱动每次 NMI 上传一个 Tile。按每秒 60 次 NMI 估算，这一屏的字模上传就需要约 2.4 秒，清屏和文字缓冲提交还会增加等待时间。玩家在翻页时感受到的停顿，也就能对应到这些具体工作上。

要缩短这段等待，可以先统计原游戏的任务占用了多少 VBlank 时间，再用剩余时间在每帧上传多个 Tile。每帧能多搬一些字形，准备同一页文字需要的帧数就会减少。

整段译文变长，增加的是页面数量；当前页用了多少种字形，决定了这一页的缓存和上传开销。PRG 保存整段文本与字库，CHR-RAM 只作为当前页的工作区，这就是这次实现解决容量问题的分工。
